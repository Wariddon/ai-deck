# Integrating team work and handling conflicts

Independent Session Team jobs use isolated worktrees. Native writers within one team stay serial. Auto Team split assignments remain disjoint by repository path; integration checks run on a temporary combined candidate, not on either writer's source. A passing source test does not certify the combined result.

The existing Compare worktrees action records working changes, new files, staging, branch, HEAD and physical Git identity. A later staging-only change requires another comparison even when working file bytes match. Choose one version when both lanes select the same or overlapping path. A rename is displayed as its deletion and addition, so select both sides when transferring the rename. Git's normal checkout line-ending rules still apply to tracked text.

Combining selected paths creates a separate uncommitted task. Updating a base creates another task on the verified current project commit. Both operations preserve the original task, staging, untracked files and ignored local files such as `.env`; ignored files are not exported as new files. Replay requires distinct physical checkouts from the same Git repository and rechecks source HEAD, branch and staging. Existing merge/rebase/cherry-pick/revert/bisect operations must finish first. Updated-base tasks additionally verify managed-folder ownership and the source's complete comparison before publication.

Same-line, rename/edit, rename/delete, binary or file/directory conflicts stop the candidate rather than resolving the choice automatically. A failed candidate is discarded; its source worktrees remain available. Source changes during a copy or review invalidate that result. A reviewed combined candidate must retain the exact files and required-check snapshot through the final review. These operations do not commit, push or send another model request on their own.

Undo Apply uses only its recorded inverse patch. It verifies the original branch/commit, staging and current files before review and again before application. Text receipts retain unique applied postimages and their observed line positions. Unrelated edits can remain when those positions and contexts are intact. Inserting/removing lines above a recorded hunk, relocating its block, replacing its applied lines or introducing ambiguous copies requires manual review. This conservative boundary prevents reversal at a different matching block. Added/deleted files require the recorded whole-file state; an unrelated replacement is never removed to undo an earlier deletion. Older receipts can reverse an unchanged file, but cannot authorize reversal across nearby edits without the new position guards.

Evidence is scoped: controlled provider fixtures exercise production app IPC, while temporary Git repositories and actual Node checks prove the named integration cases. They do not prove arbitrary repositories, every merge driver/submodule workflow, live-provider behavior or a deployed release.
